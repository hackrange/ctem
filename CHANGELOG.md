# Changelog

All notable changes to open-ctem are documented here.
Format: [Keep a Changelog](https://keepachangelog.com/en/1.0.0/)

## [Unreleased]

### Added
- **Dashboards**: build your own from a catalog of 26 widgets across vulnerabilities, devices and EDR, exceptions, GRC and Cyber Threats, on a drag-and-resize grid. Widgets are computed per viewer (scoped users see only their devices; threat and GRC widgets follow page access). Share privately, with roles or with everyone; only the owner and admins edit, others view, star or copy; admins see all dashboards. Favorites (star) appear in the menu. AI help when enabled: describe a widget, describe a dashboard, or explain one (numbers only are sent). GridStack.js 14.1.1 vendored and served locally.
- Vulnerability dashboard (*Vuln Dashboard*): headline tiles, open findings over time by severity with KEV, new vs fixed per day, aging against SLA, mean time to remediate, open findings by device type, and top vulnerabilities and devices, filterable by range, source and device type. Trends are rebuilt from finding dates (history from day one); the unfiltered view is rebuilt every 15 minutes. Charts use Apache ECharts 6.1.0, vendored and served locally.
- Vulnerabilities list: admin and cyber can tick vulnerabilities (with select-all; picks survive paging and searches) and create exceptions for them in one go, for every device or for a tag. Exceptions page: a Revoke button on each active exception, and select-all with Revoke selected on the Active tab; one required note covers them all.
- Device findings and a vulnerability's affected devices: a select-all box in the header of the selection column picks every row on the page (it shows partly checked when only some are); picks carry across pages and searches, and the exception button shows the running count.
- Vulnerabilities: **Proof** on affected devices and device findings shows the scanner's evidence (what and where, port, fix), fetched live from Rapid7 for that finding, in a dialog that only closes from its own buttons.
- **Exceptions**: a new page and workflow. Admin and cyber create exceptions (in effect at once) and approve or reject IT users' requests; scopes are one finding, chosen devices, all devices, or a tag. A reason and an end date (at most a year) are required. Active exceptions mark their findings risk accepted, so they drop out of risk, SLA and the GRC checks, and new matching findings are covered after each sync; expiry and revoke restore them. Requesters see their approved and rejected requests. The old GRC "Risk Exceptions" panel (which allowed permanent exceptions with no effect) now shows the new exceptions.
- Curated rules: an `os_starts_with` filter (case-insensitive start of the OS name, for example "VMware ESXi"). Draft with AI is friendlier: when the fields can express a request closely, it builds that rule and adds a short note saying what it assumed, instead of refusing, and its messages suggest a way to phrase a request that works.
- CrowdStrike: hidden hosts are pulled too (shipper 1.0.7 and the direct connector, `/devices/queries/devices-hidden/v1`, same *Hosts: Read* scope). They show as having CrowdStrike with their containment state, a *Hidden* chip, and a "Hidden in EDR" inventory filter. A hidden record for a name a different, live Falcon host holds (the old copy from a reimage) doesn't overwrite it. *EDR last seen* now comes from Falcon's `last_seen` instead of the pull time. The direct connector now pages through every host instead of the first 500.
- AI: Claude on Amazon Bedrock as an AI provider, through the official Anthropic SDK's Bedrock client. Pick a region, a model and a sign-in (IAM access key, Bedrock API key, or the server's AWS credentials); the endpoint comes from the region alone. Hunt, curated rule drafts and threat analysis all use it, with the same rate limit, monthly budget and metering. Threat analysis now goes through the shared AI connector instead of calling Anthropic directly, and its failures are no longer cached for a day.
- Cyber Threats: CrowdStrike alerts carry their full detail, so the Falcon console isn't needed. The alert page adds a "What happened" summary, what Falcon did (killed, quarantined, blocked, contained), a timeline (process starts, files, network connections, DNS lookups, the detection, other alerts on the host, the last status change), the process tree with command lines, users and hashes, indicators and quarantined files, network and DNS tables, other alerts on the host, and CTEM's view of the device. Needs shipper 1.0.6 (one parser, `collector_cs_alert.py`, shared with CTEM); the detail is encrypted at rest and kept out of hunting and AI prompts. The direct CrowdStrike connector moved from the retired Detects API to the Alerts API (scope *Alerts: Read*).
- Devices: admin and cyber can mark a device Not in scope with a justification and a last day (at most a year ahead). Until it ends, the device's vulnerabilities don't count: risk 0, no open findings, left out of vulnerability affected counts and the KEV, SLA and internet-facing GRC checks; the findings stay visible, dimmed. It ends on its own (audited as `device.scope_expired`), and the inventory has a "Not in scope" status filter and chip.
- Curated rules and custom checks: `inventory_status` (in_use, shipped, lost, stolen, returned) and `seen_within_days` filters, so a check can flag devices marked shipped, lost, stolen or returned that were online in the last day. `not_seen_days` and `seen_within_days` count any sign of life: a scan, an EDR heartbeat or an AD logon.
- Curated rules: `exclude` can be a list of blocks, so a combination can be left out (a device meeting every condition of one block). New filters `sources_only` (reported by those sources and no other) and `not_seen_days` (no source has seen it for N days), for example to stop old Rapid7 scan records that are waiting for the 45-day cleanup from counting against EDR coverage.
- Curated rules can create a control check: a new `open-ctem/custom-check@1` document ("+ New check" in Admin > Curated Rules, or ask the AI to "create a check ...") defines a device population, a condition, and a count or percent with thresholds. It becomes `ctem_custom_<id>` on the GRC page (marked custom, with its remediation list) and in the check catalog FairTPRM monitors use. New filters for rules and checks: `ad_joined`, `ad_stale_days` and `sources_only` (for example, computers only AD knows about).
- Curated rules: a new `edr_contained` filter, so "not contained by CrowdStrike" can be written (it used to be misread as "not reported by CrowdStrike"). Source names are accepted in any case and by common names (`CrowdStrike`, `InsightVM`, `Defender`), and the AI is told the difference between a source and containment.
- GRC > CTEM Control Checks: click a check to open its remediation list (for EDR coverage, the active devices without healthy EDR; for KEV and SLA, the overdue findings), with search, sorting, the site's paging, links to each device and the signed CSV; the list is cached for two minutes so paging a large one stays fast. Viewing it needs `grc:read`, like the report download, and is audited.
- Device Inventory: the "Any status" menu has a Contained option that lists devices the EDR has network-isolated.
- Curated rules: an `exclude` block now leaves out a device that matches any one of its conditions (it used to need all of them), so "network devices or printers" works as written. AI drafting failures now say why (out of credit, bad key, unknown model, rate limited) and the AI is told that printers and firewalls are often typed unknown. Saving, enabling, disabling or deleting a rule re-runs its check at once, so the GRC page and FairTPRM show the new result without waiting for the daily run.
- Curated rules (Admin > Curated Rules): JSON rules in the `open-ctem/curated-rule@1` standard that scope which devices a control check counts (device type, OS text, hostname pattern, tags, sources, criticality, internet-facing; include and exclude) and move its thresholds inside the check's own bounds. With AI enabled, type the rule in plain English and AI drafts the JSON; every draft is validated and previewed (result now vs with the rule, devices kept and left out) before saving. Rules are allow-listed filters, never code or SQL, and never change stored data. Each result and each FairTPRM evidence record lists the rules that shaped it; a rule that stops validating turns its check into an error. Admin only, versioned and audited. API under `/api/v1/rules` with the schema at `/api/v1/rules/schema`
- Shadow SaaS and Shadow AI checks (v2) accept FairTPRM's Shadow SaaS inventory as well as Grip, through FairTPRM's new `GET /api/v2/shadow-saas/apps`; an app seen by both counts once, Grip AI agents still count, and FairTPRM only counts as a source once its data actually arrives
- Internet-facing critical exposure (v2) counts Rapid7 AppSec web apps: an app is internet-facing when a scanned URL points at a public host, not a private IP, single-label name, internal suffix or a domain in the integration's new **Internal domains** setting
- Risk register edits go to FairTPRM: admins and the `grc` role can change a risk's status, review date and treatment plan from the GRC page, on any risk, including ones people created in FairTPRM. CTEM sends who made the change; FairTPRM keeps the before and after values. Other fields stay FairTPRM-only. Refusals (read-only token, older FairTPRM, missing risk) are explained on the page and change nothing. API: `PUT /api/v1/grc/risks/{id}/review`. The mirrored risk now keeps its treatment plan, encrypted at rest
- GRC page shows FairTPRM assessment results: the latest completed assessment's FairScore, compliance, progress, per-domain scores against maturity targets and per-framework compliance, a list of every assessment (each opens to a searchable gap list) and audits with their findings. Gaps and findings are encrypted at rest; assessor notes, remediation text and report PDFs are never pulled. API: `GET /api/v1/grc/assessments`, `/grc/assessments/{id}`, `/grc/audits`. Needs FairTPRM's new `GET /api/v2/grc/assessments`; an older FairTPRM's 404 there doesn't fail the sync
- Cyber Threats rebuilt on the standard table: search (alert, host, MITRE ID, tactic), severity / status / source filters, sortable columns with the worst severity first, the site's paging and rows-per-page, and shareable URLs. Sources show as short codes (CS, R7, SPL, S1, MDE, XDR...). Each alert opens its own page with device, source, detected time, status, MITRE tactic and technique (linked to attack.mitre.org), description and an **Open in Falcon** link; the device links to its CTEM device page. `GET /api/v1/threat/alerts` gains `q`, `status`, `sort`, `order` and `offset` with a real total, and `GET /api/v1/threat/alerts/detail?id=` returns one alert
- CrowdStrike shipper 1.0.5 sends each alert's title, detection time, status, MITRE tactic and technique IDs, Falcon device ID and console link, and pulls every alert from the last 30 days in any status (it used to pull only new ones), so closed and in-progress alerts update. Alerts stored before this show "new" and their first-seen time (marked *) until the next pull
- Single sign-on setup wizard (**Settings > Single sign-on**, admin): pick Okta, Auth0, Ping Identity (PingOne) or Microsoft 365 (Entra ID) and get current step-by-step setup instructions with CTEM's redirect URI filled in; enter the provider's details, client ID and secret (encrypted at rest, never shown again), test the provider's live discovery document, issuer, signing keys and PKCE support, and choose SSO-and-local or SSO-only sign-in. `OIDC_*` and `AUTH_MODE` environment variables still win as the break-glass
- New `no_access` role: people signing in through SSO for the first time get the wizard's default role (No Access unless changed). Anyone whose only role is No Access sees a custom message set in the wizard and gets no session; admins pin real roles in Admin > Users, and sign-in never changes them
- Links survive sign-in: opening a CTEM page (for example from an email) while signed out returns you to it after password, MFA or SSO sign-in. Only same-site paths are accepted
- FairTPRM GRC in CTEM: the FairTPRM sync now mirrors frameworks with compliance, internal controls, the risk register, evidence status, monitors and the GRC dashboard (read-only; `pull_grc` toggle, default on). The GRC page shows real per-framework compliance, controls, evidence that's expired or expiring in 30 days, and the risk register with **risk drift**: risks treated as mitigated whose controls are ineffective, whose CTEM checks fail, that have no controls, or whose review is overdue. REST: `GET /api/v1/grc/frameworks`, `/controls`, `/risks?drift_only=`, `/evidence-status`, `/overview`
- CTEM as an evidence source for FairTPRM continuous monitors: 16 control checks (EDR coverage, host hardening, asset inventory, stale AD computers, KEV deadlines, remediation SLA, internet-facing criticals, attack paths, risk exceptions, dormant accounts, password expiry, privileged access, ITDR alerts, shadow AI, shadow SaaS, monitoring health). Each returns pass/warning/fail/error with counts only, and **never passes on stale or missing source data**. REST: `GET /api/v1/grc/checks`, `/checks/{type}` (bounded threshold overrides), `/checks/{type}/report?format=csv|json` (detail rows, Ed25519-signed, formula-safe CSV, audited), `/checks/{type}/history?from=&to=` (daily roll-up up to 400 days), `/evidence-key`
- Every check runs daily and results are kept 400 days, so audit-period evidence has no gaps
- Admins issue FairTPRM's token from the GRC page (**FairTPRM access**): a password-less `svc-fairtprm-grc` service account with the new read-only `grc_integration` role, IP-bound (whole-internet ranges refused), rate-limited, one active token at a time. REST: `POST/DELETE /api/v1/grc/fairtprm-token`
- Device assignment and status, kept in a new `device_assignments` table that syncs never write: assign a device to the person who should use it (or confirm the detected user in one click), and mark it **Shipped** (UPS, FedEx, USPS or DHL plus tracking number, linked to the carrier), **Lost**, **Stolen** or **Returned**. The inventory shows a check mark for the assigned user, flags when someone else signed in last, shows status chips and filters by status; the device page has the editors; the CSV export gains Assigned to and Status; every change is audited. REST: `PUT/DELETE /api/v1/devices/{id}/assignment`, `PUT /api/v1/devices/{id}/status`, `GET /api/v1/devices/assignable-users`, `?status=` on device lists
- New `inventory` role (and `inventory:write` permission, also held by admin): sees every device but no findings, and is the only role besides admin that can change assignment or status
- Devices link to the directory user CrowdStrike saw signing in last (`DOMAIN\user`, `user@domain`, and prefixes in `ACCOUNT_ALIAS_PREFIXES`, default `sulocal_`). Discovered Users shows assigned and detected device counts, and user risk now counts assigned devices first, then detected ones nobody assigned. `backfill_sources` links existing devices
- REST API docs at `/api/docs` for signed-in admins and cyber analysts (Swagger UI pinned on cdnjs with Subresource Integrity); still hidden from anonymous visitors
- Inventory search matches people by partial username, whether the device is assigned to them or they were seen signing in, and finds admin-alias sign-ins by the bare name (`jdoe` finds `sulocal_jdoe`)
- CrowdStrike login history (shipper 1.0.4, *Hosts: Read*): each host's last 10 distinct sign-ins, newest first, stored encrypted and listed on the device page. The detected user is the last sign-in if it's a directory user, else the newest real account in the history, with admin aliases only as a last resort, so `SpecopsClient_…` and `kioskUser0` sign-ins no longer hide the owner. Runs from an older shipper and `backfill_sources` keep what the history found
- User principal name (UPN) from AD (`userPrincipalName`, encrypted at rest with a search hash). Sign-ins in UPN form (`mark.langston@ad.acme.example`) link to that person even when the name part isn't their username; device inventory and Discovered Users search accept a full UPN (any case); the device page shows the assigned and detected user's UPN and job title, and Discovered Users shows the UPN under the username. Needs the shipper upgrade below (re-run its installer); the in-app LDAP connector reads it too
- Shipper 1.0.3: reads `userPrincipalName`. The version was still 1.0.2 after the name/title/phone fields were added, so 1.0.3 is also the first that reports it sends them
- Admin-alias sign-ins that use a first name (`sulocal_akash`) link to the one active directory user with that first name; if two people share it, nobody gets linked
- AD user profile: first name, last name, title, office phone and mobile from the directory (encrypted at rest), shown on **Discovered Users**. Phone numbers are normalized to E.164 (`+15550100199`, with `;ext=N` for extensions) using the user's AD country, falling back to `PHONE_DEFAULT_REGION` (default US); anything that isn't a real number is kept as entered. New dependency: `phonenumbers` (SBOM updated)
- Rapid7 InsightVM asset tags (cloud API and console shipper) become CTEM device tags: custom tags as `r7:<name>`, plus `location:`, `owner:` and `criticality:`. Each sync replaces them, so tags removed in Rapid7 disappear here; tags from other sources are untouched. Criticality (Very High to Very Low) sets the device's asset-criticality weight in risk scoring, and the CMDB gains Location and Criticality columns, takes Owner from the Rapid7 owner tag before the last signed-in user, and reads Environment from Rapid7 custom tags like "Production". A console account that can't read tags leaves existing tags alone
- CrowdStrike containment: a host Falcon has network-contained is marked **Contained** in the inventory, on its device page (with a banner) and in each vulnerability's affected-device list. While contained its findings can't be exploited, so they show as **info**, greyed out, and score 0 / grade A; the original score and grade stay visible beside the adjusted one, e.g. `(F 87.3 → A 0)`. Lifting containment restores normal scoring at the next sync. Device finding exports gain a Severity column
- AD account health from the shipper: last logon (`lastLogonTimestamp`), password last set, password expiry (`msDS-UserPasswordExpiryTimeComputed`), expired, never-expires, locked out, and disabled. Shown on **Discovered Users** (AD status chips, AD last logon, password set) and fed into user risk: dormant enabled accounts (no logon in 90 days; doubled for privileged ones), passwords older than a year, never-expiring and expired passwords, and lockouts add risk; disabled accounts count for 30%. Values an older shipper doesn't send are kept, not blanked
- CrowdStrike firewall and USB storage telemetry: each host's applied Falcon firewall policy (enabled and enforcing) and device-control policy (enforced with mass storage set to block all) show as **FW** and **USB block** columns, on the device page, and in the CSV export. Needs *Firewall management: Read* and *Device control policies: Read* on the API client; without them the columns stay blank instead of guessing
- Per-source shipper schedules: each source (LDAP, Rapid7 console, CrowdStrike, Splunk) has its own **Run every** (5 minutes to 1 day, validated server-side; blank uses the shipper default). The box checks in every 5 minutes and ships only the sources that are due; Splunk's look-back follows its own schedule. Schedule changes need no approval on the box
- Running a shipper installer on a box that already has one now upgrades in place instead of re-enrolling, so the key, sealed passwords, approvals and source settings all survive; `--reinstall` forces a fresh enrollment. Upgrades also move the box's cron check-in to every 5 minutes
- Device inventory shows one normalized, uppercase short host name per device (DESKTOP001); the FQDN (also uppercase) is on the device page, in a tooltip, and in its own CSV column
- Sources column lists every feed that reported a device (CS, R7, AD, QL, MDE, ...), and the source filter matches any of them. `python -m api.maintenance.backfill_sources` fills it for existing devices
- Type column shows a server / workstation / network / cloud icon. CrowdStrike's product type (Server, Domain Controller, Workstation) and server operating systems now set the device type; before, every CrowdStrike and AD host was a workstation
- `--upgrade` for the shipper installer: replaces the shipper code (local or Docker mode) and keeps the box key, sealed passwords and approved destinations, so no re-enrollment
- CrowdStrike now records each host's last signed-in user (direct connector and shipper), so the device inventory's User column fills in and Hunt can find a user's computers
- On-prem shippers: an agent for an internal box that reads LDAP / AD, the Rapid7 InsightVM Security Console, CrowdStrike Falcon, and a local Splunk, then pushes to CTEM over outbound HTTPS. Managed under **Settings > Shippers**
- One-file installer generated per shipper (one-time enrollment code, optional CIDR lock), with local script mode (systemd + cron) or a self-contained Docker container, plus a generic installer that enrolls with an admin sign-in
- Central shipper config: sources, hosts, SPL, and schedule are edited in CTEM and picked up at the next 15-minute check-in
- End-to-end sealed secrets: source passwords are encrypted in the browser to the shipper's own key; CTEM stores them but can't read them. Rotate once in the GUI
- Destination changes (host, port, TLS, cert pin, SPL, Falcon cloud) need `open-ctem-collector approve` on the box before use
- Staged batches are deleted as soon as CTEM confirms receipt; unsent ones retry next run
- `PUBLIC_URL` setting for installer defaults
- The shipper's LDAP reader pages through the whole directory (AD stops a single search at 1,000 entries) and selects users with `objectCategory=person`, so computer accounts aren't counted as users. The direct LDAP connector still does a single search

### Security
- SSO ID tokens are now verified against the provider's signing keys (asymmetric algorithms only) with issuer, audience, authorized party, expiry and nonce checks; every endpoint in the discovery document must be https on the issuer's host. SSO sign-ins never attach to an existing local or directory account with the same name
- Device visibility for tag-scoped users came from `owner_user_id`; with owners now detected from sign-ins, anyone who logged into a machine would have gained access to it. Access now comes only from tags or a person's assignment
- Collector API: hashed, IP-pinned push tokens scoped to one profile's integrations; single-use, atomically claimed enrollment codes; rate-limited enrollment and sign-in; payloads parsed only after auth, with nothing echoed back or logged
- Directory pushes (and direct LDAP syncs) no longer overwrite local break-glass accounts
- Hunt never tries live SPL against a shipper-fed Splunk
- Client IPs can no longer be spoofed with `X-Forwarded-For`; API token IP binding and sign-in rate limits use the address nginx vetted. Upstream load balancers get a dedicated listener (`LB_BIND_IP:8085`)
- CSRF: Origin check on every cookie-authenticated write
- MFA: self-enrollment needs a verified code before it turns on, replacing an authenticator needs a current code, and MFA/password changes are browser-session only
- `MFA_REQUIRED=true` now enrolls users without TOTP at sign-in instead of locking them out
- Per-account cool-off after 10 failed passwords; no timing difference between unknown users and wrong passwords
- Locked accounts can no longer use their API tokens
- Stored XSS closed in hunt results, dashboard, CMDB, admin, and token views
- SSRF: AI model lookup goes through the guarded client; the vetted IP is pinned for every hop
- XML from Qualys and Palo Alto is parsed with defusedxml
- Ticket creation requires `findings:write`; vulnerability findings honor device-level access
- Integration secrets masked by name pattern; changing an endpoint requires re-entering credentials
- Errors no longer echo exception text or internal IPs; API docs hidden unless `DEBUG=true`
- Input validation on users, roles, branding, profile, hunt, and integration schedules
- Dependencies upgraded to clear all known advisories (FastAPI/Starlette, Authlib, cryptography, Pillow, Jinja2, python-multipart); python-jose replaced with PyJWT

### Fixed
- Vuln Dashboard: read-only (and other scoped) users saw fleet-wide numbers. They now see numbers for the devices they can access, cached per person, and no fleet-wide exception counts.
- GRC: the top of the page showed FairTPRM's requirement tracker at 0% for every framework. It now shows the latest assessment's results by framework, and the tracker only when a framework has progress.
- CrowdStrike shipper (1.0.8): every pull since 1.0.4 failed with a bare `HTTP 400` before any host was sent, because Falcon refused an optional extra call (login history) and that error stopped the whole run. Login history, the firewall and USB policy lookups, and hidden hosts are now extras: a refused call turns only that feature off, says why in the shipper's log, and the pull goes on (login history also falls back from v2 to v1). Shipper errors now include the API's own one-line reason, so the next failure shows what Falcon objected to.
- Database: new enum values (such as a new integration vendor) were never added on Postgres at boot, because `ALTER TYPE ... ADD VALUE` was sent with a bind parameter, which Postgres rejects; the failure was logged only at debug level. Values are now checked against a strict identifier pattern and added, and a failure is logged as an error.
- Cyber Threats showed blank Alert, Device, MITRE, Detected and Status columns: the page read field names no connector wrote. The list also kept only the first 200 CrowdStrike alerts of each batch and its paging ignored the page number
- The SSO authorize request wasn't URL-encoded, and IdP error replies (for example access denied) or failed callbacks showed raw errors instead of the sign-in page
- `ctem_exposed_criticals` passed when no device was marked internet-facing; with no exposure data it now reports an error
- Admin > Users listed every person discovered in AD/LDAP (the Discovered Users page read from the admin endpoint). Admin > Users now shows only accounts that sign in to CTEM: local accounts, token-only service accounts, and SSO sign-ins
- Discovered Users reads from a new `GET /api/v1/directory/users` (admin and cyber), which lists only directory people, with search applied to the total
- API tokens with an expiry date failed with a server error on SQLite (timezone-naive comparison)
- `install.sh --upgrade` pulled new code but never rebuilt the app, worker and beat images, so a server kept running the old code while reporting success. It now rebuilds them (and does the same on rollback), and honors a local `docker-compose.override.yml`
- CrowdStrike shipper: a firewall or device-control policy API that returns 404 now leaves that column blank instead of failing the whole CrowdStrike run
- A slow Rapid7 console (or a proxy in front of it) failed the whole run with "The read operation timed out": the shipper asked for 500 assets per page with a 2-minute limit. It now starts at 200 per page with a 5-minute limit and, on a timeout, retries the same position with 100, 50, then 25 rows instead of giving up
- CMDB looked empty: the hostname sort put bare-IP scanner assets (no FQDN, no OS) first, Owner only used an explicit owner (never set), and Environment only read `env:` tags. Named hosts now sort before bare IPs, Owner falls back to the last signed-in user, Environment comes from an `env:` tag or the AD OU path (Prod, Dev, QA, Stg, UAT, Test), and the FQDN is filled from Rapid7's full host name where it was missing (`backfill_sources` repairs existing rows)
- CMDB showed only the first 200 devices and reported that as the total. The page now pages server-side (25 to 200 per page) with the real total, search (hostname, FQDN, OS), type filter and sorting; tag-scoped users no longer see devices counted twice; the ServiceNow JSON export is no longer cut off at 10,000 CIs and carries the normalized name, FQDN, sources, firewall and USB fields
- Devices were duplicated across sources because every connector matched on the exact host name: CrowdStrike and AD report `DESKTOP001`, Rapid7 reports `desktop001.ad.acme.example`. The Rapid7 copy showed EDR as missing and no user. Devices now match on a normalized host key (short name, case-insensitive; parent and child domains count as one, a bare short name goes to the AD-joined record or the main domain, unrelated domains stay apart), Rapid7 fills in the FQDN, and `python -m api.maintenance.merge_devices` folds existing duplicates together (dry run by default)
- CrowdStrike hosts under network containment were shown as having no working EDR
- Shipper batches over the load balancer's body limit (a 500-user AD batch with group memberships easily passes 1 MB) failed with HTTP 413 and stayed spooled, so every later run hit the same wall. Batches, including ones already spooled, are now split to stay under 768 KB per request
- Shipper LDAP read Active Directory as plain OpenLDAP (ldap3 files `supportedCapabilities` under `supported_features`), so it searched for `inetOrgPerson`/`device` and shipped zero users and computers while reporting success. AD is now detected correctly, and `open-ctem-collector test` fails when the bind works but no users are visible
- Local-mode shipper installs on boxes where the installer's `umask 077` left `/opt/open-ctem-collector/venv` root-only, so the service user failed with `203/EXEC Permission denied` and nothing ever shipped. The venv is now built world-readable (root-owned), re-running the installer repairs an existing one, and the install stops if the service user can't run it
- Two syncs of the same integration could run at once (Sync Now during a scheduled run) and insert duplicate rows; a per-integration lock now makes the second one skip. FairTPRM suppliers without a security rating show as "unrated" instead of grade A
- FairTPRM integration imported nothing while reporting success: it called a `/api/v1/suppliers` endpoint with an `X-API-Key` header, but FairTPRM's API is `/api/v2` with Bearer tokens. The connector now uses `/api/v2/vendors`, takes the latest security rating per vendor (risk score, grade, open high/critical issues) and FAIR loss estimates, accepts a base URL with or without `/api/v2`, and fails the sync with a clear reason on 401/403 (bad token or CTEM's IP not on the token's whitelist)
- Grip's `fairtprm_grip_passthrough` option silently skipped the Grip sync on the assumption FairTPRM relays Grip data; it doesn't, so the option is now ignored. ITDR, posture, shadow SaaS and shadow AI come from CTEM's Grip integration only
