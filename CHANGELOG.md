# Changelog

All notable changes to open-ctem are documented here.
Format: [Keep a Changelog](https://keepachangelog.com/en/1.0.0/)

## [Unreleased]

### Added
- **Age of vulnerabilities**, for Infrastructure, Code and Web apps alike: days from when it was first found until today (or until it was fixed), from each source's own first-found date (InsightVM, Rapid7 AppSec, GitHub Code Review; for GCR site scans, the earliest scan CTEM has seen). The Vulnerabilities list shows each vulnerability's age (its oldest open finding), and the affected-assets and device findings tables show each finding's, all sortable, red once past the SLA for the severity (critical 15, high 30, medium 90, low 180 days), with the first-found date on hover. The API returns `first_found`, `age_days`, `sla_days` and `past_sla`, the Vulnerabilities list filters with `min_age_days`, and the CSV exports add First found, Age (days) and Past SLA, ready for a control check or dashboard. Each vulnerability's oldest open first-found date is kept with its affected count, so sorting and filtering by age stays fast. A source that sends no first-found date ages from when CTEM first stored the finding.
- **Data access per person** (Admin > Users > Edit > Data access). Give someone the assets, findings and dashboards where a tag role matches any of several values, for example executive owner is `Elmer Fudd` or `elmer.fudd@acme.example`, on top of what their roles give. Roles and values are picked from what is in use; matching goes through the tag mapping (so every tool's owner tags count), ignores case, accepts wildcards (`*@acme.example`, `app:*`) and picks up tags that appear later. **All assets** (`all = "*"`) gives complete visibility, tagged or not, for a CISO or an audit team, while what they can change still comes from their roles. Each user's rules show as copyable rule text (`executive_owner = "Elmer Fudd" OR executive_owner = "elmer.fudd@acme.example"`) that can be pasted on another user and applied, then adjusted. A live preview shows how many tags and assets the rules match. Changes are audited.
- **Dashboards that show everyone all the data, with approval and a time limit.** Every widget still shows each viewer only what they may see. A dashboard's Data shown can be set to Everything, so people limited to their own assets see the whole picture there. Admins and cyber set it directly, for 1 day, 7, 30, 90 or 365 days, or no end. Anyone else asks for it: the dashboard keeps each viewer's own access until cyber or an admin approves it for a time (from a bar on the dashboard, which approvers can open even when it is private) or denies it. When the time runs out it goes back to each viewer's own access by itself, and if anyone other than an admin or cyber changes or publishes it after approval, it goes back too and asks again. It applies only to the widgets as published: the server runs its stored copy, never one a browser sends. Requests and decisions are audited, and the dashboards list marks the ones waiting.
- **Count by Findings, Unique or Fixes** on the Vulnerability Dashboard. Unique counts each vulnerability once however many assets have it; Fixes counts each patch, upgrade or rollup once (a fix counts as critical, KEV or exploitable when any finding it resolves is). The headline tiles follow the switch, and the choice is remembered and kept in the link.
- **Fixes.** Findings now carry the fix their source recommends: InsightVM's solution for each finding (including rollups that supersede many older patches) and, for open-source packages, one upgrade per package to the version that resolves all its advisories. The dashboard shows the fixes that remove the most risk, and a new Fixes page (`/vulns/fixes`) ranks every fix (known exploited, then critical, then high, then volume), filters by KEV, critical or exploit available, searches, and shows each fix's steps, links and the vulnerabilities it resolves, with a link to the assets that need it (`/devices?fix=`). Steps are stored as plain text with http(s) links only. Existing findings get their fix on each source's next full sync.
- **Search assets by tag.** The Assets search box also matches tag names and values, so `specops` finds assets tagged `app:SPECOPS` and `pat@` finds those with `app_owner:pat@acme.example`. It searches within what the viewer can already see.
- **Why this score, everywhere.** Every asset page shows the reason beside its grade: for hosts, which findings the score averages and what drives the worst one (CVSS, EPSS, known exploited, criticality, EDR, exposure); for repositories and sites, the worst finding, the breadth bonus and the arithmetic. Each Code and Web app finding's Details shows its own reason.
- **Owners an asset's source doesn't give** (say, a site whose scanner sends no application owner) are filled in from other assets of the same application, labeled as such, read through the tag mapping. When nobody has one, the page says the source didn't provide it and where to add it.
- **Risk for Code and Web apps on their own terms.** Repositories and sites no longer use the host formula, whose EPSS weight (only CVEs have it), "no EDR" and "offline" adjustments meant nothing for them (every site with one critical finding scored 49.5). A finding's score is how bad it is (the geometric mean of severity and the strongest exploitation evidence: known exploited, EPSS, the tool's likelihood, a secret confirmed live, a scanner's proof, a package the code reaches; much lower when the code is unlikely to reach it), scaled by where it lives (0.5 to 1.0 from impact: a criticality tag, the data held or the environment; and exposure: a live public site, or code behind one). Context scales rather than adds, so a minor finding stays minor on a production site. The tool's own rating is averaged in when there is one (GCR's 0-100 risk for code, its risk level for site scans), and a known-exploited finding is never below 80. An asset scores its worst finding plus a point for each further serious one (at most 10). The asset page shows **Why this score**, including the arithmetic. Host scoring is unchanged.
- **Exceptions and false positives reach the tool the finding came from.**
  - Exceptions have a kind: **Exception** (the risk is accepted until its end date) or **False positive** (not real; checked again on its end date). Covered findings become risk accepted or false positive.
  - The vulnerability and asset pages have a **False positive** button beside the exception button. Admin and cyber create either straight away; anyone else who can see the findings sends a request that cyber or an admin approves (the vulnerability page now lets them request too).
  - When an exception or false positive is approved in CTEM, each GitHub Code Review finding it covers gets the same in GCR: a code finding gets an exception request (approved there too when the token has GCR's approve scope; otherwise it waits for a GCR admin), and a site finding gets an exception or false-positive decision. Each finding records what was sent and shows it in Details; nothing is sent twice, failures are retried after the next sync, and a setting turns it off. A GCR sync never reopens a finding CTEM has accepted.
- **Scanner telemetry in CTEM, so nobody has to open the scanner's portal.**
  - Rapid7 AppSec findings now carry the root cause (URL, method, parameter), the original and attack values, the scanner's message and proof, CWE and OWASP references, the score and vector, the request it sent and the response it got (cookies, authorization headers and token-like values removed), and the attack's description and recommendation (fetched once per attack). The portal link stays as an optional button.
  - GitHub Code Review code findings carry GCR's own risk score with the impact and likelihood reasons, the AI validation (rating, confidence, summary, why, what to check, compensating controls), supply-chain signals, reachability with direct or transitive and runtime or dev, the description, branches, who committed it (name only), links to the file and commit, and what the repository holds.
  - GitHub Code Review site findings carry every affected URL, references, the engine, and GCR's risk with its reasoning.
  - A vulnerability's page has a **What the scanner found** panel for Code and Web app findings (the write-up, how to fix it, the proof and evidence), and each finding's **Details** view shows the same plus the request and response.
- **Findings by type: Infrastructure, Code and Web apps.**
  - Every finding and vulnerability has a type (`domain`): infrastructure (hosts, network devices, cloud), code (repositories: SAST, open-source packages, secrets, IaC) or web (DAST and web app scanning). Connectors set it as they write (GitHub Code Review splits by asset: a repository's findings are Code, a site's are Web); anything else takes its source's type, and an hourly job brings older rows in line.
  - The Vulnerability Dashboard and the Vulnerabilities list have four pressed-in tabs, Infrastructure (default), Code, Web apps and All, remembered per browser. The source list follows the tab. On the dashboard, All shows the three side by side and never adds them together; the list adds a Type column and the export a Type field.
  - Asset pages for repositories and sites show what matters for them (application, owners, live sites in front of a repository, the code behind a site, URL, environment, grade) instead of IP, OS and EDR, and their findings show kind, where (file and line, or package and version, or URL), the fix, reachability and a **Details** view with the branch, rule, weakness, advisory, fixed version, evidence and a link back to the tool. Secret values are never stored.
  - The Security Overview has the same four tabs: Infrastructure (grade, known-exploited and total cards for hosts, top risk devices, exposure by environment, identity tiles), Code (the same for repositories, how many sit behind a live site, top risk repositories with open findings, exposure by application) and Web apps (sites, internet facing, exposure by environment), and All side by side. Cards, Top risk and the known-exploited list follow the tab and keep it when clicked through.
  - Repositories and sites are not devices: the inventory is now **Assets** with Hosts (default), Repositories, Web apps and All tabs, each with its own title, search hint and columns (a repository's application, owner and whether a live site is in front of it; a site's environment, IP and whether it faces the internet). The device API, summary and export take `asset` (hosts, repositories, sites) and the summary `by` (environment or application) and reports `internet_exposed`.
  - A vulnerability's page says Affected repositories or Affected sites for Code and Web findings and lists where in each. Repositories and sites keep their full names instead of the shortened host name.
- **GitHub Code Review integration (SAST and DAST)**: reads the platform's token API (`reports` scope, plus `external` for DAST).
  - Repositories become **Code** assets (`code_repository`) with their code, dependency (CVE, KEV, EPSS, reachability), credential and misconfiguration findings, the AI review's fix, and approved exceptions as risk accepted.
  - External sites become **Web application** assets (`website`) with telemetry (IP, grade), owners and environment and the findings of their latest finished DAST scan.
  - Application, owners, environment and visibility arrive as tags in CTEM's neutral forms (`app:`, `exec_owner:`, `tech_owner:`, `app_owner:`, `env:`), so Admin > Tag mapping, dashboard filters and owner views pick them up. A **tag map** in the integration settings tags repositories and sites by name pattern (`acme/claims-portal* = app:Claims Portal, exec_owner:Jane Doe`), checked when saved.
  - Code behind a live site counts as internet exposed, and a device CTEM knows that answers on a live site's IP is marked internet exposed.
  - Findings GCR no longer reports are marked remediated after a complete read; nothing is written back to GCR. Only the configured https host is called, through the SSRF-safe client, with bounded paging.
- Dashboard data logic and AI follow-ups:
  - **Widget filters**: "only count devices where..." conditions on tags (is, is not, starts with), tag-mapping roles (for example Executive owner is Jeffrey Davis; values compare as the dashboards show them), sources (reported or not reported by a tool), device type, OS family, criticality and risk grade, matched all (AND) or any (OR). Every device-based widget honors them; filtered widgets show a badge, and cards keep exact tag and source filters when they click through. Snapshot trends and non-device widgets (alerts, exceptions, GRC) aren't filterable.
  - **Conditions on any data source and value**: besides tags, a widget can filter on device values grouped by where they come from: Directory (AD OU, last AD logon, in AD), Vulnerability scanner (last seen, risk score, open and KEV findings, internet exposed), EDR (last seen, sensor working, contained, hidden, product, host firewall, USB blocking), Device (hostname, FQDN, OS, OS version, first seen) and Cloud. Text values take contains, starts or ends with and their negatives, equals and empty; numbers take over and under; dates take older than or within N days, or never. Columns and operators are allow-listed and values are bound.
  - **Filters you can see and change in edit mode**: a widget's conditions show as chips under its title, each with an x to remove it; click a chip or "+ Filter" to refine them. View mode shows the data without the filter controls.
  - **Dashboard-wide filters**: in edit mode a filter bar under the title applies conditions to every widget that counts devices, on top of each widget's own, saved with the dashboard (draft and publish like everything else). The data, CSV export and Explain use them, and Edit with AI sets dashboard filters for whole-dashboard requests ("leave out OU=Blocked_Computers").
  - **AD OU filter** ("leave out OU=Blocked_Computers", any depth, any case). The DN stays encrypted: each device keeps keyed hashes of its OU names (`ad_ou_keys`), filled on directory sync and backfilled hourly.
  - **The AI says when it changed nothing**: an AI edit that leaves the dashboard as it was now comes back as "The AI couldn't make that change: ..." instead of looking like it worked, and the AI is told which widgets can't be filtered.
  - **"Only devices I have access to"**: a filter that applies the viewer's tag grants and assigned devices even for roles that see everything, resolved per person on shared dashboards. Widgets already show each viewer only the devices they may see; per-user tag grants will plug into the same place.
  - **CSV export** on every table and chart widget, built on the server for the person exporting (their access and the widget's filters), formula-safe.
  - **Keep refining with the AI**: in edit mode an "Ask the AI" box applies one change after another to what's on screen (unsaved work included) and remembers what was already asked, so follow-ups like "now make the 44-day card red" build on it. A dashboard the AI drafted carries its first request over.
  - **The AI asks when unsure**: when a request is unclear in a way that changes the result (which threshold, which tool, whose devices), the AI asks one short question with suggested answers instead of guessing. The answer goes back with the request, and it won't ask about the same point again. Works for new dashboards, single widgets and Edit with AI.
- Dashboard builder, easy enough to use without the AI:
  - **Widget library to drag from**: in edit mode a side panel lists about 50 stock widgets grouped by topic (risk overview, remediation, environment, asset inventory, coverage and tagging, vulnerability trends, operations) plus every catalog metric. Drag one onto the grid or click it to add it; move, resize (corner or edges) and duplicate widgets in place.
  - **Switch chart types on the widget**: each widget shows its chart types as one-click icons, color dots and a transparency setting while editing.
  - **New chart types**: gauge, stacked bars, columns, pie, scatter and bubble, and bars with a line on a second axis (for example open findings with the risk score). Number cards show the change from a month ago (green when it's good news) and a sparkline. Charts show a one-line takeaway such as "12.4% decrease in open findings over the last month".
  - **Transparency** per widget (solid down to 25%) and soft gradient fills on areas.
  - **Themes**: Default, Ocean glass, Sunset, Forest, Violet glass, Slate outline and Neon glass. A theme changes the non-severity colors and the card style (solid, see-through glass, or outline); severity colors never change meaning. Everything is drawn from the site's color tokens and redraws when you switch between light and dark.
  - **Starter dashboards**: Risk overview, Remediation progress, Environment trends, Asset coverage, Asset inventory and Vulnerability trends, in the New dashboard dialog.
  - **Draft, publish and share**: new dashboards are private drafts. Once published, edits save as a draft that only the owner and admins see, while everyone else keeps the published version until the owner publishes again. You can also discard the draft or unpublish. Share sets the name, who can see it and gives a link to copy.
  - **Responsive**: the grid drops to 6 columns on tablets and 1 on phones, and charts resize with their widget.
- Risk and asset widgets (vendor generic):
  - **Risk**: average risk score (gauge, with a month-ago comparison), vulnerabilities vs risk score over time (optionally cloud vs on-prem), new and remediated vs risk score, remediated share, mean time to remediate (with the change from the period before), mean time to remediate cloud vs on-prem, accepted risk and its trend, assets over time by their worst severity, top vulnerabilities split cloud vs on-prem, and a CVSS-by-EPSS bubble map sized by affected devices.
  - **Assets**: counts by type and OS family, optionally only those without EDR or a vulnerability scanner; operating system families; newly seen assets; obsolete or unsupported software (gauge); assets with critical vulnerabilities; certificate problems from scanner findings; assets over time cloud vs on-prem; EDR and scanner coverage over time; tag coverage (criticality, any owner, application, location...) using Admin > Tag mapping; and a device risk map.
  - **Trend history**: open, new and fixed counts are rebuilt from finding dates, so they have history from day one. The risk score, severity mix, accepted risk and coverage come from a daily fleet snapshot (hourly job, heavy counts once a day) and fill in from now on. Snapshot trends are shown to people who can see every device.
  - Asset cards click through to the same devices: the device list, summary and export take `os_family`, `missing` (edr, scanner, either), `active_days`, `new_days` and `compute`, shown as removable chips.
- Dashboards, built to what people ask for:
  - **Directory widgets**: stale AD computer objects and stale AD user accounts at any threshold (1 to 3650 days without a logon), the stalest computers as a list (last logon, OU), and stale objects over time at 21, 30 and 90 days. The stale-computer card opens the device list filtered to exactly those objects (`/devices?ad_stale_days=N`, shown as a removable chip; the device API, summary and export take `ad_stale_days`).
  - **Trends for counts with no history of their own**: an hourly job records today's stale counts per threshold (`metric_snapshots`), so the trend fills in from now on rather than being guessed from last-logon dates.
  - **Per-widget style**: a color (blue, green, red, orange, yellow, purple, teal, gray) and, for single numbers, amber and red thresholds with "higher is worse". Set in the widget editor, cleaned on the server like every widget field.
  - **Edit with AI**: describe a change ("make the stale trend blue", "add a 14-day card", "turn the donut into bars"); the AI's version opens in edit mode with a note of what changed, and nothing is saved until Save. Owners and admins only.
  - **AI drafting composes instead of refusing**: it sees every widget's options and the style choices, uses a metric several times with different options (for example three cards for 90, 30 and 21 days), builds the closest match with a note on anything it assumed, and refuses only when nothing in the catalog is close.
- **Cloud Inventory** (Cloud in the menu; admin and cyber): every AWS, Azure and OCI instance with what makes it breachable. Cards that filter: cloud instances by provider, **Breachable now** (reachable from the internet with a KEV finding or grade F), internet exposed, not scanned, no EDR, and cloud only (in no other tool). Each row: the instance and its CTEM device, provider, account and region, public IPs, reachability (ports open to the internet, rules limited to specific sources), the attached firewalls, scanner and EDR coverage, open and KEV findings, grade and owner (from Tag mapping). Filters by provider, account, region and condition, search by name, hostname, IP or resource ID, sortable, CSV export. API under `/api/v1/cloud`.
- Cloud tags: AWS instance tags, Azure VM tags and OCI freeform and defined tags become device tags (`aws:ITOwner:Jeff Davis`, `azure:Environment:Prod`, `oci:Ops.Owner:...`), so Tag mapping can read them (its suggestions pick up owner, application, environment and cost-center keys). Each provider's tags are kept in step with the cloud on every sync; AWS's reserved `aws:*` keys are skipped.
- Device detail, visibility for real exposure: **Public IP** lists every public address observed for the device and where it was seen (the cloud integrations today); **Host firewall** (renamed from "Firewall (EDR policy)", also in the device list and CSV) shows Active or Off with the EDR policy it comes from; **Cloud firewall** shows whether the cloud lets the internet in and on which ports, and names the attached firewalls (AWS security groups and network ACLs, Azure NSGs on the interface and subnet, OCI security lists and NSGs). **View effective rules** opens a dialog (it closes only from its own button) with, per cloud record, the attached firewalls, every effective inbound rule (port, who can reach it, exact sources, the rule that allows it), the implicit deny for everything else, and how that cloud's rules were combined. Cloud syncs now record the attached firewalls.
- **Admin > Utilization** (admins only): CPU, memory and disk gauges for this server, refreshed every 5 seconds; a storage breakdown (the disk, every database on the PostgreSQL server, CTEM's biggest tables with data and index sizes, the write-ahead log, Redis); and history charts from an hour to a year. A banner warns at 80% disk (red at 90%) and estimates how many days until the disk fills from the past week's trend, since a full disk stops PostgreSQL from accepting writes. A beat job records a row a minute (kept 2 days) rolled into hours (kept 400 days). Numbers come from /proc, the filesystem and PostgreSQL's own size functions; no Docker socket is used.
- **Cloud exposure: AWS, Azure and Oracle Cloud (OCI) integrations** (read-only). Each reads every instance's private and public IPs and what its cloud firewalls let in: AWS security groups and network ACLs, Azure NIC and subnet network security groups (evaluated by priority; both must allow), OCI security lists and NSGs. Every open port gets a reach: *internet* (a public IP and a rule open to any address), *any address but no public IP*, or *listed sources only* (CIDRs, other security groups, prefix lists). Instances match their CTEM device by private IP (by name when an IP repeats across networks), or become new cloud-instance devices; the device's *Internet exposed* now comes from these facts, and terminated instances are forgotten. Scoring reads the ports per finding: a finding on a port open to the internet isn't discounted, one reachable only from listed sources (a bastion, an admin IP) is ×0.6, and one no rule allows is ×0.4, each with its reason on the **Reach** chip. Device detail has a **Cloud exposure** panel (public IPs, open ports, who can reach them, the rule). Credentials: AWS access key (plus an optional role to assume for other accounts; EC2 Describe calls only), Azure app registration with Reader, OCI API signing key with read access. Only the providers' own endpoints are called, from allow-listed region and cloud names; secrets are stored encrypted. `boto3` is now a direct dependency (it was already installed through the Bedrock SDK).
- **Rule exceptions** (admin only): on the Exceptions page, **+ Rule exception** creates an exception for every device and vulnerability a rule describes (`open-ctem/exception-rule@1`), for example "device names starting with CAN with an OS starting with Cisco IOS" for legacy gear reachable only through a bastion. Devices use the curated-rule filters (hostname pattern, OS starts with or contains, device type, tags, sources, criticality...); vulnerabilities are optional (CVE IDs, title words, CVSS range, KEV or not, source), and leaving them out covers every vulnerability on those devices. Describe it in plain words and the AI drafts the rule (it never writes the reason or controls), or edit it; **Check** previews the devices, open findings and any KEV findings it covers before **Create** unlocks. It stays dynamic: each rescore covers new matching findings and releases findings on devices that stop matching. Same rules as every exception: a reason, compensating controls (required here) and an end date at most a year out. It can cover up to 100,000 devices; above 50 hosts (or with any KEV finding) the preview warns how many hosts it will exclude, and creating asks you to confirm that number. Revoking releases everything. API under `/api/v1/exceptions/rule` (`/preview`, `/draft`, create).
- **Admin > Tag mapping**: say what your tags mean. Built-in roles (Executive owner, Technical owner, Application owner, Application, Environment, Location, Business unit) and your own each take prefixes ("starts with") or exact tags, case-insensitive; when several match a tag the longest wins, and the value shown is the tag without the prefix (optionally title-cased). A live preview shows how many devices and which values a role matches, and **Suggested from your tags** proposes prefixes found in your real tags (for example a scanner's `owner:E-O:` or a cloud `itowner:` tag) to add in one click. The dashboard's tag filters (one per role marked as a filter), the tag-focus chips, and the CMDB Owner, Environment and Location read the mapping; the code ships with neutral defaults only (`exec_owner:`, `tech_owner:`, `app_owner:`, `app:`, `env:`, `location:`, `bu:`). Admin only, versioned and audited (`tag_role.*`); your tags are never changed. API under `/api/v1/tag-roles`.
- GRC > CTEM Control Checks, four inventory-hygiene checks, each with a remediation list that says what to fix and where. A record counts as stale after 21 days (adjustable):
  - **Stale records in security tools** (`ctem_stale_tool_records`): devices still listed in a vulnerability scanner, EDR or directory that nothing (scan, EDR heartbeat or directory logon) has seen in 21 days, with counts per category and, per device, which tools still hold it (R7, QL, CS, S1, AD...) and each category's last date, so someone retires them there.
  - **Stale directory computers in no other tool** (`ctem_orphan_ad_computers`): directory (AD) computer objects with no logon (`lastLogonTimestamp`) in 21 days that no scanner or EDR has ever reported, with their DN, to disable or delete.
  - **On the network, EDR silent** (`ctem_edr_silent_on_network`): workstations and servers the scanner saw in the last 7 days whose EDR agent hasn't checked in for 21 days (on the network but probably not getting EDR policy), including hosts hidden in the EDR console. Devices with no EDR at all stay under EDR coverage.
  - **Active, not scanned** (`ctem_scan_gap`): workstations and servers with an EDR heartbeat or directory logon in the last 7 days that the vulnerability scanner hasn't seen in 21 days, or ever (a scanner, agent or credential failure, or a coverage gap).
  All four are written per tool category, so any supported scanner (Rapid7, Qualys, Tanium, Defender), EDR (CrowdStrike, SentinelOne, Defender, Cortex XDR, Tanium) or directory counts. They are device-scoped (curated rules apply), show on the GRC page and are available to FairTPRM monitors. AD's logon time replicates with up to about 14 days of lag, so keep AD-based windows at 14 days or more.
- Device inventory and device detail: **Last seen** is the freshest sign of life from any tool (Rapid7 scan, CrowdStrike heartbeat or AD logon), shown as days ago with the tool that saw it; the hover lists each tool's date, and sorting uses the same value. The API adds `last_seen_by`, `seen_by` and `scan_last_seen` (the scanner's own date).
- Tag focus: an owner, application or environment filter picked on the dashboard (or a `/devices?tag=...` link) follows you in that browser tab: the Devices list and the sidebar link keep it, device detail shows it with a back link to the filtered list, the Vulnerabilities list and a vulnerability's affected devices, count and CSV export include only those devices, and the dashboard restores it. Each page shows the focus as chips; removing a chip clears it everywhere. `GET /api/v1/vulns`, `/vulns/{id}`, `/vulns/{id}/findings` and their exports take `tag` (repeatable, at most 10), on top of the viewer's own device scope.
- Reachability, first step: each Rapid7 finding records where it was found: on a listening network service (with its ports, for example `443/tcp 8443/tcp`) or by a local check with no listening service tied to it. With the CVSS attack vector (now read from CVSS v2 when v3 is missing), this sets one reachability factor per finding: physical access ×0.3, local access ×0.5, adjacent network ×0.8, local check ×0.75; listening services and NodeZero-confirmed findings are not discounted. Device and vulnerability finding lists have a **Reach** column whose hover text is the reason. Device and finding scores change on the next rescore; filled in by the next full InsightVM Cloud sync.
- Device detail: more than 5 tags show the first 5 and a "+N more" toggle, which reads "Show fewer" while open.
- Shipper 1.0.9: `open-ctem-collector set-url https://new-host` points a shipper at CTEM's new address when the hostname changes, with no re-enrollment and nothing re-entered. It switches only when the new address answers as open-ctem over verified HTTPS, accepts the shipper's own token and returns its own profile (a different CTEM install is refused); the box key, approved destinations and sealed passwords stay as they are. Every shipper command, its log and the installer now print the agent version first, and `--version` prints it.
- **Dashboards**: build your own from a catalog of 26 widgets across vulnerabilities, devices and EDR, exceptions, GRC and Cyber Threats, on a drag-and-resize grid. Widgets are computed per viewer (scoped users see only their devices; threat and GRC widgets follow page access). Share privately, with roles or with everyone; only the owner and admins edit, others view, star or copy; admins see all dashboards. Favorites (star) appear in the menu. AI help when enabled: describe a widget, describe a dashboard, or explain one (numbers only are sent). GridStack.js 14.1.1 vendored and served locally.
- Vulnerability dashboard (*Vuln Dashboard*): headline tiles, open findings over time by severity with KEV, new vs fixed per day, aging against SLA, mean time to remediate, open findings by device type, and top vulnerabilities and devices, filterable by range, source and device type. Trends are rebuilt from finding dates (history from day one); the unfiltered view is rebuilt every 15 minutes. Charts use Apache ECharts 6.1.0, vendored and served locally.
- Vulnerabilities list: admin and cyber can tick vulnerabilities (with select-all; picks survive paging and searches) and create exceptions for them in one go, for every device or for a tag. Exceptions page: a Revoke button on each active exception, and select-all with Revoke selected on the Active tab; one required note covers them all.
- Device findings and a vulnerability's affected devices: a select-all box in the header of the selection column picks every row on the page (it shows partly checked when only some are); picks carry across pages and searches, and the exception button shows the running count.
- Vulnerabilities: **Proof** on affected devices and device findings shows the scanner's evidence (what and where, port, fix), fetched live from Rapid7 for that finding, in a dialog that only closes from its own buttons.
- **Exceptions**: a new page and workflow.
