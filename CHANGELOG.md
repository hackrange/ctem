# Changelog

All notable changes to open-ctem are documented here.
Format: [Keep a Changelog](https://keepachangelog.com/en/1.0.0/)

open-ctem is a Python rewrite of an earlier PHP version begun about 18 months before this repository; that history isn't in this repository (see [docs/project-overview.md](docs/project-overview.md)). Versions here start with the Python release, and each version is tagged `vX.Y.Z` at the commit that finished it. The on-prem shipper has its own version numbers.

## [Unreleased]

## [1.29.5] - 2026-11-28

### Fixed
- "Why C, risk 54/100?" on an asset listed reasons (say, "A pentest exploited it here") without saying what: which finding they were about, or which pentest. It now names the finding that weighs most, as a link to its vulnerability, and the NodeZero pentest that proved it and when (found on the finding, or on the pentest's own finding for that CVE merged into it), with a link to the Pentest tab. An asset shows it from its next rescore. The explanation also stays valid when its reasons are long (the least telling are dropped instead of the text being cut).

## [1.29.4] - 2026-11-28

### Changed
- Documentation reviewed for production. README: what's needed to run CTEM; API docs are admin-only; all 25 control checks; the real roles; full `docker compose` commands for maintenance; that installed servers start with `AUTH_MODE=local_only` and `MFA_REQUIRED=false` and when to change them; a certificate for running without the installer; when an upgrade can't roll the code back; a link to the new SECURITY.md. The project overview describes the risk-based model (and admin sign-ins) and points to this changelog for versions. The integration page is a public status table. `.env.example` documents every setting the app reads, says to clear the first admin's password after first sign-in and what `PUBLIC_URL` is for, and no longer lists two settings that upgrades then flagged as new.
- Figures, names and events from one deployment are gone from the changelog, docs and code comments; examples are generic.

### Added
- SECURITY.md: how to report a vulnerability privately, what's in scope, and how releases are checked.

## [1.29.3] - 2026-11-28

### Changed
- The automated test suite (`tests/`) and its settings (`pytest.ini`) are no longer published in the repository; they aren't needed to run CTEM. They stay with the maintainers, and every release still passes them before it ships. Both are in `.gitignore`. Earlier releases' history still contains them.

## [1.29.2] - 2026-11-28

### Changed

The version line at the top is current again (it said 1.15.0).

## [1.29.1] - 2026-11-28

### Security
- The CTEM image and the shipper image run Python 3.13.18 (were 3.12.16 and 3.12.15), pinned to an exact Python version (`python:3.13.18-slim-bookworm`) rather than a moving tag. That carries the fixes for CVE-2026-115557 and CVE-2026-3446 (the latter has no 3.12 fix). The full test suite passes on 3.13.18. Rebuild Docker shippers to pick it up; a shipper installed without Docker now prefers python3.14 or 3.13 when the box has them. CVE-2026-115559 (and four more) and CVE-2026-124249 are fixed only in CPython 3.16, not released yet.
- A software title's "reported as" names came from every asset, so a person who sees only some assets also saw the exact names (versions included) reported on others. They now come only from that person's assets, like the rest of the title.

### Changed
- SBOMs for both images, always current: `sbom.cdx.json` (CTEM) and the new `sbom-collector.cdx.json` (shipper), each built inside its exact base image by `scripts/make_sbom.sh`, and each naming its base image and Python runtime as well as every package. The precheck fails when either falls behind a pinned package or a base image.

## [1.29.0] - 2026-11-28

### Added
- An admin signing in interactively raises a host's risk (impact, through the privileged-credentials factor the model already had but nothing set). Workstations, where admins should use runas or sudo: any admin as the last sign-in +40%, an admin among recent sign-ins only +25%, with no exceptions. Servers: an account in a privileged AD group +40%, an admin-named account +25% (the admin sign-in check's patterns plus Administrator and root), recent only +10%; servers the admin sign-in check's curated rules leave out (jump servers) don't count. The score's reasons name it. Most hosts it affects move one grade (A to B, B to C). A change of last sign-in rescores the host; recent sign-ins and AD group changes count at the nightly full rescore.

## [1.27.0] - 2026-11-27

### Added

After each Okta sync, active alerts with no person, the same title, source IP and Okta reason, each within 24 hours of the last, are one alert with a count (x28) and its first and last time seen; the repeats are resolved with a pointer to it, not deleted.

## [1.26.2] - 2026-11-27

### Fixed
- Every CrowdStrike firewall policy with port ranges looked changed on every shipper upload, so every host on it was rescored for nothing (thousands of hosts, minutes of rescoring, each time). The ranges arrive as pairs that Python keeps as tuples and read back from the database as lists, and a tuple never equals a list, although the stored JSON was byte for byte the same. Policy bodies are now kept as stored JSON and only written when they differ, and the rescoring check compares JSON values in their stored form. Rules keep the order CrowdStrike reports; a real change, including the rules in another order, still rescores the policy's hosts.

Some CrowdStrike shipper uploads mark thousands of devices whose score inputs end up unchanged; this shows what does it.

## [1.25.2] - 2026-11-27

### Fixed
- Updating a CrowdStrike alert from Cyber Threats always failed ("The server refused that"): the audit entry recorded the alert's key (about 110 characters) as its resource id, a 36-character column, so Postgres refused the insert and the whole update rolled back. An audit resource id longer than the column is now stored as its UUIDv5 (the same for the same resource, so still searchable), and the alert update's audit detail names the alerts. The tests had missed it because SQLite doesn't enforce column lengths; they now check the stored id fits.

## [1.25.1] - 2026-11-27

### Fixed
- The daily EPSS refresh (over a thousand requests to FIRST covering every published CVE, several minutes) threw away every score it had fetched when one request failed near the end (FIRST rate-limits), so every post-sync run after that spent those minutes again asking and failing again, holding rescoring back. It now keeps what was answered and stops at the first refused request; the next run asks only for the rest.

## [1.25.0] - 2026-11-27

### Added
- Pause syncing on the Integrations page (admins): all integration syncing stops for 30 minutes, 1 hour, 4 hours or until resumed. No scheduled sync starts, Sync Now and already-queued syncs are skipped, and on-prem shipper uploads are refused with "send again on the next run" (the shipper keeps its data). Running syncs finish and scoring carries on, so the worker can drain before maintenance. A banner shows who paused it and when it resumes; a timed pause ends on its own; both changes are audited. Kept in the database, so it holds across restarts.

## [1.24.1] - 2026-11-27

### Changed
- A Linux distribution's own packages are system components, not third-party software (thousands of "Linux ..." titles on a large Linux estate, all shown as third-party before). A scanner reports every Linux package with the vendor "Linux"; the distribution's own carry its release tag in the version (el8_10, amzn2023, ubuntu, deb12u, a SUSE 15 build number). Vendors' packages built for a distribution (falcon-sensor, mysql-community, Oracle jdk and others) and packages with no tag (a vendor's agent, database client tools, Chrome) stay third-party. Stored titles are reclassed once.

### Fixed
- Tanium's software from Linux endpoints is named like a scanner's ("Linux <package>"), so it meets the same title, and a Windows product Tanium reports without a vendor no longer joins a Linux package of the same name (a Windows security agent had landed on the "Linux" title of the same name; it moves at the next Tanium sync).
- A title whose product name is only an edition word after its vendor ("Enterprise" from Splunk, titled "Splunk Enterprise") was renamed to the bare vendor on the next regroup and back on the next upload; it keeps its name now, and a regroup never tries to create a title that already exists.

## [1.24.0] - 2026-11-27

### Changed
- One software title per product whichever tool reports it. Titles are keyed by their normalized name, not vendor and name, so vendor spellings ("SolarWinds Worldwide, LLC" and "SolarWinds") are one title, and a name sent without a vendor (Tanium) joins the title that is that name led by its vendor ("PuTTY release" and "Simon Tatham PuTTY release" are "Simon Tatham PuTTY"). Versions in brackets ("- (2024.2.0.50539)") and a trailing "release" are dropped from titles. Stored titles regroup once (often by a quarter or more), keeping the strictest review decision and exceptions.
- One vulnerability per CVE across InsightVM and Tanium: a Tanium finding uses InsightVM's catalog entry when InsightVM has a check about that CVE alone (never a bundle check), so the Vulnerabilities page lists the CVE once with every affected machine, and an exception on it covers both tools. Existing Tanium findings move at the next Tanium sync; Tanium's emptied catalog rows are removed.
- Identity > person: the cards open what is behind them. Identity risk shows its parts, Leaked, Reused and Weak passwords filter the password table to those apps, and ITDR alerts and Posture findings go to their lists.

### Fixed
- The Vulnerability Dashboard could say it couldn't load: a filtered view nobody had opened in the last 30 minutes was built during the request (tens of seconds with a large set of Tanium findings) and the proxy gave up. Each view is now built once and kept: visits answer at once from the last build and an old build is redone in the background; a view never opened before is built once for everyone asking (the page shows that it is being built), at most two at a time per app process.

## [1.23.0] - 2026-11-27

### Added

## [1.22.1] - 2026-11-26

### Fixed
- A sync cut off by a worker restart (a deploy, a crash) no longer stays "running" for good or holds back that integration's syncs for 3 hours. ## [1.16.0] - 2026-11-26

### Added
- IDV Approvers role (permission idv:approve): the only role that can approve, decline or revoke an identity verification. Admin and cyber still see the IDV page; an admin who should decide adds the role.
- IDV review dialog: click any row (or Review, now right after the name). Shows why the check needs a decision (each failed Persona check, what it means and what to validate before approving), what the person presented (government ID type, country, capture method, selfie, result), the key checks, device and network, how it was started, and the person's other attempts.
- For approvers, read live from Persona when the dialog opens and never stored: the name printed on each ID next to the directory name (match or no match), and each session's ISP, network, connection type, country by IP and by GPS. Each look is audited.
- Decisions take a reason from a fixed list plus a note; the reason is shown on the request and sent to Persona.

## [1.14.0] - 2026-11-25

### Added
- **Risk-based scoring, on by default.** Each finding is scored by how likely it is to be exploited, whether an attacker can reach it on that host, and what it would cost, combined as a weighted geometric mean, so one weak dimension isn't averaged away: a CVSS 10 flaw with a 0.2% EPSS on a host with no listening service drops, while a guessable SNMP community on a live service rises.
  - **Likelihood:** the strongest of KEV, EPSS (counted in full at 20%), a pentest's proof and threat-actor use, after the EDR's protection (what its policy blocks, exploit mitigations for memory flaws) and days offline.
  - **Reachability:** from evidence instead of "unknown counts as half". A pentest's result first, then a listening service (internet-facing or internal, through the cloud firewall where known), a client-side flaw (higher on workstations, where people browse and open files), or a flaw needing the same segment, local or physical access; host firewall rules and segmentation scale it down.
  - **Impact:** severity and asset criticality, raised where the host holds privileged credentials.
  - **Admin > Risk model:** the weights, likelihood values and reachability ladder, each beside its default; Reset restores them, and turning it off returns to the classic CVE-weighted score. Every change is audited and rescores the fleet.
    An internet-facing host with no data on which service a flaw sits on gets its own rung; a flaw the scanner saw on a live port counts as reachable whatever NVD's attack vector says, but a local or physical vector never gets the internet-facing rung. Client-side rungs apply to workstations and servers only, not network appliances.
  - On a sample of 1,000 random devices, the top 1% of findings holds two thirds more KEV findings and seven times as many with EPSS of 10% or more, and half as many that are only "CVSS 9 or above". B-grade findings fall by more than nine tenths. Hosts with something actively exploited move to D or F (the share at D and F nearly triples); C nearly empties.
  - The settings API takes strict numbers only, and the audit log records every value that changed, old and new.

## [1.13.2] - 2026-11-25

### Security
- **Accounts and API tokens are sealed (CTE-031).** Whoever could write to the database, without the app's keys, could take over an account without touching a secret. They could copy a known authenticator secret into an admin's row (anyone mid-enrollment holds one, readable in their session cookie), switch an admin's MFA off so it re-enrolled, write in a password hash they knew, add the admin role to their own account, or add an API token row for anyone. Now:
  - each account carries a keyed seal over its sign-in state and roles (password hash, MFA on or off and its secret, active, locked, local or SSO identity, the first-password flag, when its sessions were last ended, its page access), and each API token and shipper credential one over itself (a planted shipper credential would otherwise be sent future secrets sealed to its own key);
  - the seal is checked on every request and at each sign-in step before anything is written, so a planted role or token opens nothing and a tampered account is never offered enrollment;
  - only CTEM's own changes re-seal, and only with the state they checked (a role slipped in while a change runs is not sealed in): admin create, reset, roles, enable and disable, unlock, authenticator setup and removal, the person's own enrollment and password change, new SSO accounts, issuing, editing and revoking tokens, enrolling and revoking shippers;
  - an admin change to an account someone else edited is refused (409). **Admin > Users > Repair** trusts nothing it held: the admin picks its roles and whether it's active, a local account gets a new one-time password, its authenticator goes, and an SSO account loses its identity link;
  - View As refuses such an account, and a stored SSO setting can never make admin the default role for new sign-ins.
- **Upgrading: seal the existing accounts once.** `install.sh --upgrade` does it (re-running a failed upgrade finishes it; it keeps a marker on the host, not in the database), and every restore does it for what it restored. After a manual upgrade, run `docker compose exec app python -m api.maintenance.seal_accounts`. Until it runs, nobody can sign in. It never runs at app start or from anything stored in the database, so a database writer can't trigger it. An account refused afterwards was changed outside CTEM: an admin resets it. Accepted, not covered:
  - a database writer can replay a row's own earlier state with its earlier seal, from a copy taken before a change (an old backup's password hash, a revoked token);
  - what each role is allowed to do (role permissions), device tags and assignments, and the access rules built on them are not sealed. A database writer could widen a role, though not to admin or cyber, which are checked by name;
  - changing `ENCRYPTION_KEY` breaks every seal; `seal_accounts` restores them by trusting the database as it is then, so check it first.
- **A password an admin sets is a one-time key (CTE-035).** Creating an account or resetting a password marks it to be replaced at the first sign-in, and it expires after 72 hours (`INITIAL_PASSWORD_HOURS`). That sign-in asks for the person's own password before anything else, MFA enrollment included, and the MFA step can't be skipped to. Shipper enrollment refuses such an account until it's done in the browser. Someone who learns the given password later, or after it expires, holds nothing.

- **NodeZero findings belong to their integration.** A Horizon3 sync deleted every NodeZero finding it didn't see, whichever NodeZero account reported it, and cleared every "exploited by a pentest" flag before setting its own. Findings are now tied to their integration. Only a run's own findings are matched, closed or deleted, and nothing is deleted for an unnamed integration. The exploited flag is worked out from every integration's open, proved findings. Older untagged findings are taken over while there is a single Horizon3 integration.

### Changed
- Signed-in self-service (authenticator enrollment, profile preferences, password change) moved to `api/routes/auth_profile.py`; the routes are unchanged.

Gone hosts lose their findings daily at 03:30 UTC; the asset record stays, its Last seen updates the moment any tool sees it again, and when the vulnerability scanner reports it again CTEM reads its whole finding list on that same sync (not just what's new), so its findings are back within hours, not at the next weekly full sync. ## [1.1.0] - 2026-11-19

### Security

- CSRF: Origin check on every cookie-authenticated write
- MFA: self-enrollment needs a verified code before it turns on, replacing an authenticator needs a current code, and MFA/password changes are browser-session only
- `MFA_REQUIRED=true` now enrolls users without TOTP at sign-in instead of locking them out
- Per-account cool-off after 10 failed passwords; no timing difference between unknown users and wrong passwords
- Locked accounts can no longer use their API tokens
- Stored XSS closed in hunt results, dashboard, CMDB, admin, and token views
- SSRF: AI model lookup goes through the guarded client; the vetted IP is pinned for every hop
